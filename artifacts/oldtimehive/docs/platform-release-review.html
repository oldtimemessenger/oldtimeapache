1. Added-music publishing failure

The supplied stack names the older production chunk app-js2qzE6i.js. Its error text identifies an AudioContext startup timeout during export. The supplied diagnostic has no upload request or HTTP response: it is evidence of a client-side audio failure, not evidence of rejected Cloudflare storage authorization. The currently served production entry is different; an already-open editor can still execute its previously loaded code. Existing edits must not be force-reloaded or cleared.

Two concrete code-level problems were identified:

  1. The original renderer created a context after asynchronous preparation rather than necessarily using the context activated by the Publish tap. The earlier deployed correction handed the gesture-started session to video export, but genuine iPhone behavior remained unverified.
  2. The added-sound first-reuse path still called captureAudioExcerpt() after rendering reached 100%. That path constructed another AudioContext, awaited resume and started a separate media element. Consequently, a successful render did not eliminate a second audio-activation boundary before upload. Separately, the renderer started added music through an independent media element.

Important uncertainty: these are confirmed source defects and the automatic regression exercises them. No genuine iPhone reproduction is available to prove which operation or OS state caused the specific reported attempt. The old stack must not be presented as proof that a new candidate has failed or succeeded. The physical-device root cause remains unverified.

Candidate changes

  • Use the tap-started session for both video rendering and post-render sound-excerpt recording. The excerpt step does not create a new context when invoked from this editor.
  • Fetch and decode selected music into an AudioBuffer, then route buffer sources through gain nodes into the recording destination. Added music no longer depends on a preview media element starting playback or a speaker connection.
  • Keep the original video audio connected to the recording destination. Silent/explicitly muted exports do not require an audio graph. Unknown audio metadata is never treated as proof of silence. Unchanged eligible Stories may use the same original-file path as feed posts.
  • Support both suspended and interrupted context states. Retain genuine native exception names and stacks; annotate resume, sound loading, decoding and destination creation. HTTP sound failures retain status, bounded response text and request ID where available; signed query parameters are excluded from the diagnostic request URL.
  • Stop temporary buffer sources, tracks and recording connections; keep an active editor's bound context available for retry and release it on disposal. Failures do not clear the composition or report publication success.

This does not bypass browser security. A blocked context, unavailable native encoder or denied original-video playback can still stop an edited-video export with a real error. No silent soundtrack removal or quality-reducing fallback was added. A universally reliable fallback for such failures has not been established on iOS.

3. PWA versus Capacitor

PWA: a standalone web manifest and service worker already exist. This is the least disruptive browser/install-on-home-screen route, but installation does not remove iOS audio, lifecycle or background-execution constraints. A PWA is not automatically an App Store or Play Store release.

Capacitor: the most practical option to evaluate for store apps while retaining the existing UI and Cloudflare backend. No Capacitor configuration or native iOS/Android project was found in the current app. A wrapper alone will not fix the audio pipeline. Prototype native media/encoding, secure-session, lifecycle and transfer adapters before committing to it. Current Capacitor documentation includes camera recording/gallery and app-state/deep-link APIs; pin and verify the chosen plugin versions and device behavior.

Principal risks are native file URIs versus browser Blobs, permission timing, decoder/encoder availability, API origin trust, session restoration, safe areas and keyboard behavior, process suspension, plugin maintenance and separate store-review/signing workflows. Do not migrate frameworks or replace the website before the findings and prototype are reviewed.

6. Reproducible iPhone and Android checks

  1. Keep the original failing tab and edit intact. Do not clear website data or force reload it. Run the following in an authorized candidate environment once device access and an approved account are available.
  2. Record OS version, device, browser/standalone mode, candidate build identifier, source codec/resolution/frame rate and selected music identity.
  3. Run separate clips with original audio only, no audio track, explicit original mute where supported, and added music. For music, set a known offset/volume and an obvious musical transition. Repeat with 30 and 60 fps sources.
  4. Trace sound resolution/loading, decode, context state, mixing, render completion, excerpt recording, upload authorization, transfer, finalization and post creation. Save native exception name/stack, failed request, HTTP response and request ID when one exists.
  5. Check 100% render is not called publication. Confirm the stored media and actual server-created post before declaring success. Retrieve the result from Cloudflare and play it in feed/profile, with source audio and selected music audible and synchronized.
  6. Induce a connection failure and retry without closing the editor. Confirm the composition/music remain and only one post is created. The stable-key retry path now has isolated client/server regression coverage; verify it on the device and live account.
  7. Repeat after a phone call/audio interruption, background/foreground, screen lock and low-power mode. Check denial messages remain truthful and do not cause silent exports or false successful posts.
  8. Repeat on a slower Android device and another iPhone class; test Safari, installed PWA and, later, actual WKWebView/Android WebView builds. Other iOS browsers must be assessed on their actual engine; do not infer engine support solely from a brand name.

7. Practical release plan

  1. Website update: the duplicate-retry gap now has stable keys, an atomic D1 record, and isolated replay tests. Real-device and authenticated production media checks remain the next release evidence; this review does not claim them.
  2. Website release: after explicit publishing authorization, publish the additive D1 migration, Worker and Pages changes; run a controlled real post and playback smoke check. Preserve current records and open editing sessions.
  3. Native feasibility: review a small Capacitor proof of concept with native media and secure-session adapters, not a framework rebuild. Keep the same Cloudflare backend and existing website.
  4. Store candidates: distribute through TestFlight and Play internal testing; verify signed device builds, camera/library/microphone permissions, app links, authentication, media export, lifecycle and uploads. Prepare icons, privacy disclosures, data-safety/permission declarations and account-deletion behavior.
  5. Store submission: confirm UGC reporting/blocking/moderation and audio reuse rights, platform SDK/target requirements at submission time, app-review credentials and release rollback procedures. Apple minimum-functionality review means a web wrapper alone is not guaranteed approval. Do not enable unverified billing or push simply for store submission.
